## What works

### M1 — Skeleton
Solution with the six specified projects plus `Stigsmith.AppHost` / `Stigsmith.ServiceDefaults` (Aspire). .NET 10,
nullable, `TreatWarningsAsErrors` from the first commit. EF Core 10 + Npgsql schema with the `InitialSchema` migration.
Aspire host (API + Postgres + pgAdmin + Ollama) and a `docker-compose.yml` fallback. CI on a bare runner plus a
container job and an Ollama job.

### M2 — Checklist ingest
`.ckl` and `.cklb` read **and** write; XCCDF 1.1/1.2 results and ARF collections import. Format detected from content,
not extension. **Both review formats round-trip byte for byte**, including fields Stigsmith does not model, verified
three passes deep. Cross-format exports pinned to golden files. `.cklb` uuids derived from rule identity so two exports
of an unchanged checklist are the same bytes.

Fixtures are generated by `tools/make_fixtures.py` from a 72-rule synthetic RHEL 8 catalog: both formats, a three-host
mixed-format set, OpenSCAP-shaped XCCDF and ARF, and an edge-case `.ckl`. All synthetic, `*.example.test` with RFC 5737
addresses, **asserted by test rather than by review**.

### M3 — Rule classification

```
72 rules: 47 automatable, 9 manual, 16 needs-review (65% automatable).
Of 45 open: 29 automatable, 6 manual, 10 needs-review.
22 automatable rules are high-risk and need explicit opt-in.
```

Five ordered heuristic steps over `fixtext` and `check content`, no model. High-risk tagging (sshd, PAM, SELinux,
firewall, authentication, network) at **100% recall against the answer key, 0 false positives of 72**.
`GenerationEligibility` gates generation on per-domain opt-in and always requires a check-mode path.

### M4 — Convention retrieval
`AnsibleRoleIndexer` reads a role from a **runtime-configured path** (constraint 5: nothing vendored) and extracts per
task the name, module, variables, notified handlers, `when` guards, tags, and derived rule ids. Each task's **raw YAML
is sliced from the file**, so the few-shot example keeps the operator's formatting. `RoleConventions.Infer` extracts the
house style and renders it for the prompt. Retrieval is **BM25 with an exact same-rule shortcut**.

### M5 — Generation
`IRemediationProvider` with Ollama as the **default, not a fallback**. Prompt assembly keeps the model in translation
mode and offers `# cannot-automate:` as a first-class answer. `AnsibleYamlExtractor` handles bare, fenced, and
prose-wrapped responses and **reports** invalid YAML rather than repairing it. Bounded `Channel` + `BackgroundService`,
one job at a time, streaming over SignalR. Every generation persists the **full prompt, model, parameters, prompt hash,
and retrieved examples before the model is called**.

**Constraint 3, measured:** 424 prompts assembled from every finding in every fixture, 48 host values searched for in
each, **zero found**, plus canary assertions, `FindingDetails`/`Comments` absence, and a reflection check that
`RemediationRequest` cannot reach host metadata.

### M6 — Validation sandbox
The loop, in order: `ansible-lint` → `--syntax-check` → (`--check`, for high-risk rules) → apply → **re-scan** →
apply again and require zero changes. **Each attempt gets a fresh container.** Exactly one repair attempt with the tool
output fed back verbatim; failing again lands in `needs-human-review`. Both attempts stored as separate rows.

Verification is a real `oscap xccdf eval` where the datastream has the rule, otherwise DISA's own check command run as
a read-only shell test — and **which one ran is recorded**, because they are not worth the same. A rule neither can
verify does not pass.

**End-to-end result:** 14 automatable rules validated with full evidence, all passing; one deliberately-broken rule
correctly landed in `needs-human-review` with the lint error preserved.

API: `POST /api/generations/{id}/validate`, `POST /api/checklists/{id}/validate`,
`GET /api/checklists/{id}/validation-report`, `GET /api/validations/{id}`,
`GET /api/generations/{id}/validations`, `GET /api/validations/status`.

## The 37 skipped tests — read this before trusting M5 or M6

This machine has **no Docker, no Ollama, no `ansible-lint`, no `oscap`**. Concretely:

| Not verified here | Covered by | Consequence |
|---|---|---|
| `DockerValidationSandbox` — **never executed at all** | `DockerSandboxTests` (all skipped) | **The largest caveat in this repo.** Container lifecycle, file injection, exec, and the full loop against a real container are unrun code. |
| A real model's Ansible surviving the loop | needs both Docker and Ollama | Nothing here says a real model writes good Ansible. |
| The live Ollama call | `OllamaProviderTests.Generates_against_a_live_ollama` (skipped) | The provider's request body, NDJSON parsing, mid-stream errors, and availability probe *are* tested through the real class with a stub handler. |
| Import/export/generation/validation endpoints and the EF migration against real Postgres | the `ApiFixture` suites (skipped) | The logic underneath is covered by tests that do run. |

CI mitigates this: **`container-tests` builds the validation image and runs the Docker suites**, and `ollama-tests`
pulls a model and runs the live generation test. **Until `container-tests` has gone green, treat the Docker path as
unrun.** That is the first thing to check.

The scripted doubles are honest about their limits. `ScriptedSandbox` models a coherent world — it tracks whether
remediation was applied, so the verifier genuinely fails before and passes after — and `ScriptedRemediationProvider`
cycles the four response shapes real models produce. Neither says anything about the real thing.

## What I am uncertain about

1. **`.cklb` has no published schema.** This reader was derived from observed STIG Viewer 3 output. Four specific
   uncertainties are listed in the remarks on `CklbReader`. Mitigated by re-emitting the whole source document on
   export, so a misunderstood key still survives a round trip — but a real `.cklb` from a version I have not seen is
   the most likely place M2 breaks.
2. **The M3 answer key was corrected five times while the heuristics were written.** Every correction was a genuine
   internal inconsistency in the key (all six tabulated in `DECISIONS.md`), but a key adjusted alongside the thing it
   grades is partly fitted to it. **The held-out set — `RuleClassifierTests`, 32 cases written from the policy against
   rules authored in the test file — is the stronger evidence, not the 100% agreement figure.** If you want better
   evidence, have someone who did not write the classifier key a fresh sample.
3. **BM25 retrieval drifts at ranks 2–3** on a 21-task role: after the one or two genuinely related tasks there is
   nothing close, and it ranks on incidental shared vocabulary. The top hit is right across all five tested
   subsystems. Embeddings are the upgrade path and `Retrieve` is the only thing that would change.
4. **A container cannot validate kernel, boot, or service rules.** Those fail to apply for reasons that say nothing
   about the generated Ansible. The loop reports it honestly, but it means M6's pass rate on a real checklist will be
   much lower than on the fixtures, concentrated in file/package/config rules.
5. **The SCAP profile and datastream path in `ValidationOptions` are guesses** for AlmaLinux 8
   (`xccdf_mil.disa.stig_profile_MAC-1_Classified`,
   `/usr/share/xml/scap/ssg/content/ssg-almalinux8-ds.xml`). I could not verify them without the image built. If oscap
   silently never matches, every verification falls back to check content — visible in the report's `VerifiedByOscap`
   count being zero, which is worth checking first.
6. **Few-shot examples are the operator's own role source.** If that role hardcodes an inventory hostname, that text
   reaches the model. It is their code and not scan data, so it is outside constraint 3 as written — but it is a real
   boundary and it is stated in the README rather than hidden.

## What I would do next, in order

1. **Run `container-tests` in CI and fix whatever `DockerValidationSandbox` gets wrong.** It is unrun code in the one
   component the project describes as the whole point. Everything else is less valuable than this.
2. **Point it at a real Ansible role and a real model, on one real checklist**, and read the validation report. The
   numbers that matter are: how many automatable rules produce YAML that survives the loop, and how many of those
   passes rest on a real SCAP scan rather than a check-content shell test. I would expect the first honest number to be
   disappointing, and that is the number the project lives or dies on.
3. **Verify the SCAP profile and datastream path** (uncertainty 5). If oscap never matches, the strongest evidence the
   tool can produce is quietly unavailable.
4. **Replace the container with a VM for kernel/boot/service rules** (uncertainty 4). `IValidationSandbox` is the seam.
   This is the difference between validating a third of a checklist and validating most of it.
5. **Then, and only then, M7.** A dense keyboard-first triage UI over 1500 findings is worth building once the pass/fail
   numbers behind it are real. The spec for it is detailed and prescriptive; follow it literally.
